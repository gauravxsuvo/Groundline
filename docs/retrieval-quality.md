# Retrieval quality report

Generated by `backend/scripts/eval_retrieval.py`. Companion to `latency-report.md`: that one answers how fast retrieval is, this one answers whether it returns the right passage.

## How this is scored without hand-labelling anything

The source dataset ships MS MARCO's own relevance judgements. Each row carries `passages.is_selected`, a per-passage flag where 1 means human annotators said that passage answers the query. `build_index.py` already carries that flag onto every chunk's metadata, so the labels are sitting in the index.

For each evaluation query we retrieve the top 5 and ask whether the passage annotators picked came back, and how high:

- **recall@5**: the annotated passage appeared somewhere in the top 5.
- **MRR@5**: 1/rank of the first annotated passage, 0 if absent. Rewards putting it first rather than fifth.

Queries whose source row has no selected passage are skipped, since there is no ground truth to score against. 1,200 queries per run, fixed seed, drawn from the same cached benchmark set the latency report uses.

This is a genuine relevance measure rather than a proxy, with one caveat worth stating: MS MARCO marks the passage annotators chose, so a different passage that also answers the query counts as a miss. The absolute numbers are therefore a floor, and comparisons between configurations, which is what this report is for, are unaffected.

## Result: fusion weighting was costing real accuracy

The original implementation fused dense and BM25 rankings with reciprocal rank fusion at equal weight, the textbook default. Measured, that default was the single largest quality problem in the retrieval path.

| Strategy | Chunks | Tuned hybrid recall@5 | Tuned MRR@5 | Dense only recall@5 | BM25 only recall@5 | Equal-weight RRF recall@5 |
|---|---|---|---|---|---|---|
| passage_native (production) | 49,885 | **0.891** | **0.621** | 0.891 | 0.634 | 0.801 |
| metadata_aware | 49,885 | 0.891 | 0.621 | 0.891 | 0.634 | 0.801 |
| hierarchical | 49,885 | 0.891 | 0.621 | 0.891 | 0.634 | 0.801 |
| fixed_window | 65,691 | 0.872 | 0.609 | 0.874 | 0.607 | 0.772 |
| semantic | 68,938 | 0.871 | 0.599 | 0.868 | 0.603 | 0.787 |

Equal-weight RRF scored **0.801** recall@5 against dense retrieval's **0.891** on the production strategy, and the same 9-point gap holds on all five strategies. BM25 is simply much weaker on this corpus (0.634), and at equal weight RRF lets it reshuffle a stronger ranking with noise: RRF credits by rank position only, so BM25's rank-1 result carries exactly as much weight as the dense rank-1 result regardless of how much worse it is.

`metadata_aware` and `hierarchical` scoring identically to `passage_native` is the expected result, not a bug: all three index the same passage text and share one embedding matrix, as documented in PLAN.md Phase 1.

### The weight sweep

`python scripts/eval_retrieval.py --sweep` splits the 1,200 queries in half, sweeps on the dev half and reports the chosen setting against the held-out half. Dev MRR@5, `passage_native`:

| dense:sparse | rrf_k=10 | rrf_k=20 | rrf_k=30 | rrf_k=60 |
|---|---|---|---|---|
| 1:1 | 0.521 | 0.516 | 0.515 | 0.514 |
| 2:1 | 0.571 | 0.557 | 0.554 | 0.550 |
| 4:1 | 0.601 | 0.585 | 0.577 | 0.569 |
| 8:1 | 0.615 | 0.606 | 0.599 | 0.589 |
| 12:1 | **0.619** | 0.613 | 0.610 | 0.596 |
| 20:1 | 0.618 | 0.616 | 0.614 | 0.608 |

Monotonic and saturating: quality climbs with dense weight and flattens around 12:1, which is where `rrf_dense_weight` is set. Held-out check at 12:1 with `rrf_k=10` gives recall@5 0.887 / MRR@5 0.624 on the test half against dense-only's 0.887 / 0.625, so the setting generalises rather than fitting the dev split.

### Why BM25 stays in the pipeline

The sweep says dense-dominant weighting recovers dense-only accuracy, which invites the obvious question of why keep sparse retrieval at all. Two reasons, both load-bearing:

1. **It is what the off-topic guardrail runs on.** Raw BM25 top score goes to exactly 0.0 when a query shares no vocabulary with the corpus. Dense cosine has no such floor, it sits around 0.65 even for keyboard mash (see `input_guard.py`). The guardrail needs a signal that bottoms out, and BM25 is the only one available here.
2. **It breaks ties on exact rare terms.** At 12:1 it cannot override the dense ranking, but where dense has no strong opinion it still orders results. That is the regime it is actually good at, and confining it there is the point of the weighting.

A backstop arrangement was tested too, taking dense's top 3 or 4 and filling the remaining slots from BM25. It scored worse (recall@5 0.874 at 4+1, 0.838 at 3+2) than simply taking 5 from dense. BM25's top 5 contains a relevant passage that dense's top 5 misses on 3.4% of queries, while dense finds one BM25 misses on 29.1%, so spending a slot on it loses more than it gains.

## How many passages generation should get

recall@k on `passage_native` under the production config:

| k | recall@k | MRR@k |
|---|---|---|
| 1 | 0.448 | 0.448 |
| 3 | 0.774 | 0.594 |
| **5** | **0.891** | **0.621** |
| 8 | 0.953 | 0.630 |
| 10 | 0.964 | 0.632 |
| 20 | 0.983 | 0.633 |

`retrieval_top_k` stays at 5. Going to 8 would buy 6 points of recall, and the trade is not worth it here: the binding constraint on the generation provider is a token-per-minute budget (see `latency-report.md`), and 60% more context per request spends that budget faster, which costs latency and throttling on every query to help the minority where passage 6 through 8 mattered. MRR is nearly flat past 5 anyway, so the extra passages that do arrive land below the ones the model was already going to cite.

## Reproducing

```
cd backend
python scripts/eval_retrieval.py              # the strategy table
python scripts/eval_retrieval.py --sweep      # the weight sweep, dev/test split
python scripts/eval_retrieval.py --depth      # the recall@k curve
```

Needs the index artifacts in `backend/data/processed/` (`scripts/build_index.py` or `scripts/pull_index.py`). No API keys, no network: this is pure local retrieval, which is also why it runs in about 30 seconds across all five strategies.
